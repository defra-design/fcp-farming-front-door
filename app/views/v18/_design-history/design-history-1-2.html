UI changes

Data tables

In v1.1, only hedgerows on the map were clickable. Land covers are now clickable too, so clicking either highlights its row in the data table.

Before: v1.1

  • clicking a hedgerow highlighted its row in the Hedgerows data table
  • land covers could not be clicked

After: v1.2

  • clicking a land cover highlights its row in the Land covers data table and makes it bold
  • the land cover is outlined on the map
  • clicking anywhere else on the map clears the selection
  • where a hedgerow and a land cover overlap, the hedgerow takes the click, so only one thing is highlighted
  • on mobile, the fullscreen map's touch crosshair can also select a land cover
{# After screenshot to add: a land cover selected on the 1.2 land parcel page. #}

Why we changed it

{# Draft hypothesis, written from the research findings: check before sharing. #}
Problem
6 of 7 participants expected the map and data table to be linked. This was the most frequent usability finding in the research on v1.1.
We believe
Linking map features and data table rows both ways will help users match what they see on the map to its data.
We'll know if
Participants can match a land cover on the map to its row in the data table without help.
Technical notes

The interact plugin misses clicks on polygons that cross a vector tile boundary, which is common when zoomed in to one parcel. We used the map library's own hit test instead, and the prototype draws the selection outline itself.

Layers panel

In v1.1, the Layers panel switched whole layers on and off. Each land cover type can now be switched on and off individually, so a user can isolate individual land covers on the map.

Before: v1.1

  • 4 checkboxes: Other parcels, Land cover, Land parcel and Hedgerow
  • Land cover switched every land cover type on or off together

After: v1.2

  • each land cover type on the parcel has its own checkbox, indented under a Land cover parent checkbox
  • the parent switches all types together, and stays ticked while any type is ticked
  • choices persist after a change of base map, and reset when the user moves to a different parcel
  • the Other parcels and Land parcel checkboxes have been removed to simplify the panel

Why we changed it

{# Draft hypothesis, written from the research findings: check before sharing. #}
Problem
Participants expected GIS-style layer controls, and 4 of 7 struggled to match land cover classifications to areas on the map (research on v1.1).
We believe
Switching land cover types on and off will help users see which areas match each classification.
We'll know if
Fewer participants struggle to match a land cover classification to its area on the map.
Technical notes

The mapping component has no parent checkbox for a group of layers, so the prototype adds one. This is a prototype workaround and would need to be raised with the interactive map team for the real service.

Measure tools

The map on the [land parcel page] now has a Measure tools menu, so users can measure a distance or an area themselves.

{# Screenshots to add: the Measure tools menu open, and the Area panel showing a measurement. #}

Distance

Area

  • the menu has 4 options: Measure a distance, Measure an area, Edit measurement and Clear measurement
  • Edit measurement and Clear measurement are disabled until there is a measurement
  • a panel on the map shows the figure live as the user draws, headed Distance or Area
  • there is one measurement at a time: starting a new one clears the last
  • screen readers announce the figure each time a point is added and when the shape is finished

What the panel shows

Tool Figures
Distance Length in metres, to the nearest metre. This matches the Length (m) column in the Hedgerows table.
Area

Hectares to 4 decimal places, matching the Land covers table and the total area, so figures can be compared directly. Below that, the area in square metres and the perimeter in metres, for example 1.9638 ha, then 19,638 m² · perimeter 669 m.

Square metres are included because hectares are hard to picture for small shapes: 0.0113 ha is easier to understand as 113 m². The perimeter answers questions like how much fencing or hedging would go round an area.

Why we changed it

{# Draft hypothesis, written from the research findings: check before sharing. #}
Problem
4 of 7 participants expected measurement tools for distance and area (research on v1.1).
We believe
Letting users measure on the map will help them check parcel and land cover figures against what they see.
We'll know if
Participants can measure a distance or an area without help, and say whether they need the square metres and perimeter line. If not, it could be cut to hectares only, or show square metres only for small areas.
Technical notes

Measure tools use the interactive map's draw plugin, which is only in the newer map version (0.0.52). Figures are worked out on the curved surface of the Earth, using the same formula as the map component's own area check (@turf/area).

RPA's published areas are usually measured on the flat British National Grid, so tracing an existing land cover may differ slightly in the last decimal place. Most of the difference comes from where the user places the points, not the maths.

Data tables: change tags and arrows

When a previous version is shown, the data tables now mark every difference from the current version. Users no longer have to compare 2 sets of figures to find what changed.

{# Screenshot to add: the Land covers table with Added, Removed and Changed tags and an arrow. #}

Tags

A tag in the first cell of a row shows:

  • Added on a current row with no equivalent in the previous version
  • Removed on a previous row with no equivalent in the current version
  • Changed on both rows where an area or length has changed

Arrows

A changed value on the current tab also has an up or down arrow before it, showing whether it went up or down. It appears only on the current tab, as an arrow beside the previous value would suggest that value had moved.

Summary rows are marked the same way when totals differ. The Total rows under each table are not marked, as a total changes whenever a row above it does.

Where they appear

Layout How changes are marked
Tabbed data tables, side by side and stacked Each version of a land parcel has its own data table. Previous land parcel rows get a tag only. Current rows get a tag, and an arrow for a changed value.
Single set of tables The current version's rows, with removed covers listed at the end with their previous area and a Removed tag.

Why we changed it

{# Draft hypothesis, written from the research findings: check before sharing. #}
Problem
Most participants were not confident they had found all the changes on a parcel, and wanted to understand what had changed (research on v1.1).
We believe
Tagging each changed row, and showing which way a value moved, will help users find every change without comparing figures themselves.
We'll know if
Participants can say what changed on a parcel, and whether each area went up or down, without help.
Technical notes

The arrow is hidden from screen readers. Instead they hear increased or decreased and the previous value after the figure, for example 0.0447 increased (was 0.0225).

A value only counts as changed if it differs at the number of decimal places shown, so a tag never marks a difference users cannot see.

How these layouts work

Each version has its own column with a map. A text insert gives the previous version's date range, the last updated date is diplayed on the current version. On small screens the columns stack.

Panning or zooming one map moves the other, so both show the same area. Both open framed on the parcel. Each map keeps its own Key, Layers panel and base map.

The tables highlight each difference with tags and arrows, so users do not have to spot every change themselves.

Why we moved away from 2 maps

Participants asked for side by side views, but the need behind it was confidence that they had found every change. 2 maps still leave users to spot differences by eye, so we moved to Comparing land parcel versions on a single map. We have not tested either layout with users.

  • the layouts only fit 2 parcelversions, but parcels can have many
  • a small change is hard to see across 2 maps, but sits in one place when both versions share a map
  • side by side halves the width of each map and table, so small land covers are hard to see and table rows wrap
  • stacked maps are taller than most laptop screens, so users have to scroll between versions
  • on mobile, and when zoomed in to 200% or more, both layouts become a single column with 2 Map view buttons, and the fullscreen map shows one version at a time
  • keyboard and screen reader users go through every map control, Key, Layers panel and table twice
Technical notes

Land covers are matched by name, and covers of the same type are paired in area order. Hedgerows have no stable identity between versions, so they are matched by position. This works for the 2 example parcels but would need real identifiers in the live service.

The current version is read live from the land covers service, which only returns covers valid today. The previous version comes from a snapshot file stored with the prototype. The parcel boundary and hedgerows are fetched once and shown on both sides, as only the land covers differ in the examples.

The mapping component is not designed for 2 maps on a page: its plugins cache setup from the first map and reuse it for the second. The prototype gives each map its own copy of each plugin and its own layer identifiers. This is a prototype workaround and would need to be raised with the interactive map team if the real service needs 2 maps on a page.

Comparing land parcel versions on a single map

Problem

We believe
Switching versions on one map will make changes easier to see than looking between 2 maps.
We'll know if
Participants can tell what changed between versions using one map, without help.

How the two versions are drawn together

Both versions use the same colours, so the previous version is drawn underneath the current one, faded to about a third of its strength, with a dashed dark outline round each cover.

The outline shows where a previous boundary sat even under a current cover. A removed cover keeps its colour so its type can still be read. The Key has a single Previous version entry rather than listing every type twice.

The parcel boundary and hedgerows are the same in both versions, so they are drawn once and the version controls do not affect them.

Technical notes

The change tags in the tables come from matching the 2 versions' covers: covers are paired by name, then by area order. An unpaired previous cover is removed, an unpaired current cover is added, and a pair with a different area is changed. No geometry is compared, so a tag marks a whole cover rather than the part of a boundary that moved. This would need proper identifiers in the live service.

What we're testing next

None of the v1.2 changes has been tested with users yet. In the next round of research, we want to find out whether participants can:

  • match a land cover on the map to its row in the data table without help
  • match a land cover classification to its area on the map
  • say they are confident they have found all the changes on a parcel
  • tell what changed between versions using one map, without help
