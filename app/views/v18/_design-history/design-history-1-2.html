Design history Land summary (v1.2)

Third iteration of a prototype that re-presents the existing land summary customer journey using the Defra interactive mapping component (opens in new tab) (v0.0.22-alpha).

This iteration focused on the land parcel page. We:

  • made land covers on the map clickable
  • simplified the Key and Layers panels
  • applied both changes to the 2 historical land parcel views (SX3963 2340 and SX3964 7821)
  • added side by side and stacked pages to compare a previous version of a parcel with the current one
  • added 4 variants that show both versions on a single map

Research findings and what we are prioritising

The research on v1.1 found that:

  • Users are trying to verify information, not simply view it
  • Confidence matters more than task completion
  • Historic mapping solves a genuine user problem
  • Users expect mapping tools to behave like mapping tools
  • Adviser and agent workflows differ from farmer workflows

UI changes

Data tables

In v1.1, only hedgerows on the map were clickable. Land covers are now clickable too, so clicking either highlights its row in the data table.

Before: v1.1

  • clicking a hedgerow highlighted its row in the Hedgerows table
  • land covers could not be clicked

After: v1.2

  • clicking a land cover highlights its row in the Land covers table and makes it bold
  • the land cover is outlined on the map
  • clicking anywhere else on the map clears the selection
  • where a hedgerow and a land cover overlap, the hedgerow takes the click, so only one thing is highlighted
  • on mobile, the fullscreen map's touch crosshair can also select a land cover
{# After screenshot to add: a land cover selected on the 1.2 land parcel page. #}

Why we changed it

{# Draft hypothesis, written from the research findings: check before sharing. #}
Problem
6 of 7 participants expected the map and data table to be linked. This was the most frequent usability finding in the research on v1.1.
We believe
Linking map features and panel rows both ways will help users match what they see on the map to its data.
We'll know if
Participants can match a land cover on the map to its row in the panel without help.
Technical notes

The interact plugin misses clicks on polygons that cross a vector tile boundary, which is common when zoomed in to one parcel. We used the map library's own hit test instead, and the prototype draws the selection outline itself.

Layers panel

In v1.1, the Layers panel switched whole layers on and off. Each land cover type can now be switched on and off individually, so a user can isolate individual land covers on the map.

Before: v1.1

  • 4 checkboxes: Other parcels, Land cover, Land parcel and Hedgerow
  • Land cover switched every land cover type on or off together

After: v1.2

  • each land cover type on the parcel has its own checkbox, indented under a Land cover parent checkbox
  • the parent switches all types together, and stays ticked while any type is ticked
  • choices persist after a change of base map, and reset when the user moves to a different parcel
  • the Other parcels and Land parcel checkboxes have been removed to simplify the panel

Why we changed it

{# Draft hypothesis, written from the research findings: check before sharing. #}
Problem
Participants expected GIS-style layer controls, and 4 of 7 struggled to match land cover classifications to areas on the map (research on v1.1).
We believe
Switching land cover types on and off will help users see which areas match each classification.
We'll know if
Fewer participants struggle to match a land cover classification to its area on the map.
Technical notes

The mapping component has no parent checkbox for a group of layers, so the prototype adds one. This is a prototype workaround and would need to be raised with the interactive map team for the real service.

Layout iterations

Side by side and stacked

We built side by side and stacked pages that show the current and a previous version of a parcel together, with every difference tagged in the tables.

{# Draft hypothesis, written from the research findings: check before sharing. #}
Problem
4 of 7 participants asked for an easier way to compare versions, such as side by side views. 5 of 7 were not confident they had found all the changes, and 5 of 7 wanted to understand what had changed (research on v1.1).
We believe
Showing both versions together, with each difference tagged, will help users find every change without spotting it themselves.
We'll know if
Participants say they are confident they have found all the changes on a parcel.

Side by side

Stacked

Each version has its own column with a map. The Summary, Land covers and Hedgerows tables from the land parcel page. A highlighted panel gives the previous version's date range, and each column repeats its date so the tables line up. On small screens the columns stack.

Panning or zooming one map moves the other, so both show the same area. Both open framed on the parcel. Each map keeps its own Key, Layers panel and base map.

The tables highlight each difference, so users do not have to spot every change themselves.

A tag in the first cell of a row shows:

  • Added on a current row with no equivalent in the previous version
  • Removed on a previous row with no equivalent in the current version
  • Changed on both rows where an area or length has changed

A changed value on the current side also has an up or down arrow. It appears only on the current side, as an arrow beside the previous value would suggest that value had moved. Summary rows are marked the same way when totals differ.

Technical notes

Land covers are matched by name, and covers of the same type are paired in area order. Hedgerows have no stable identity between versions, so they are matched by position. This works for the 2 example parcels but would need real identifiers in the live service.

The current version is read live from the land covers service, which only returns covers valid today. The previous version comes from a snapshot file stored with the prototype. The parcel boundary and hedgerows are fetched once and shown on both sides, as only the land covers differ in the examples.

The mapping component is not designed for 2 maps on a page: its plugins cache setup from the first map and reuse it for the second. The prototype gives each map its own copy of each plugin and its own layer identifiers. This is a prototype workaround and would need to be raised with the interactive map team if the real service needs 2 maps on a page.

Comparing versions on a single map

{# Draft hypothesis, written from the research findings: check before sharing. #}
Problem
Users need to compare versions (see the side by side and stacked pages above). Parcels can have more than 2 versions, and can be split or merged.
We believe
Switching versions on one map will make changes easier to see than looking between 2 maps.
We'll know if
Participants can tell what changed between versions using one map, without help.

We built 4 variants to test different ways of switching between current and previous versions of land parcels. They share one map and one set of data, and differ in the control used.

How the two versions are drawn together

Both versions use the same colours, so the previous version is drawn underneath the current one, faded to about a third of its strength, with a dashed dark outline round each cover.

The outline shows where a previous boundary sat even under a current cover. A removed cover keeps its colour so its type can still be read. The Key has a single Previous version entry rather than listing every type twice.

The parcel boundary and hedgerows are the same in both versions, so they are drawn once and the version controls do not affect them.

Tabbed data table to accommodate multiple historical versions of land parcels

Technical notes

The change tags in the tables come from matching the 2 versions' covers: covers are paired by name, then by area order. An unpaired previous cover is removed, an unpaired current cover is added, and a pair with a different area is changed. No geometry is compared, so a tag marks a whole cover rather than the part of a boundary that moved. This would need proper identifiers in the live service.

What we're testing next

None of the v1.2 changes has been tested with users yet. In the next round of research, we want to find out whether participants can:

  • match a land cover on the map to its row in the panel without help
  • match a land cover classification to its area on the map
  • say they are confident they have found all the changes on a parcel
  • tell what changed between versions using one map, without help
